# 系统与源码说明

## 系统目标与运行链路

本工程接收校园赛 Unity 游戏的同帧图像、相机内参、自身状态和导航敌情，完成目标检测、跟踪预测、弹道瞄准、射击许可、能量机关击打及 Dijkstra 路径执行。

```text
Unity 游戏 ⇄ ROS TCP 桥
               │
               ├─ 图像/内参/状态 → armor_detector → tracker → aim_solver
               │                                            │
               ├─ 图像/状态 → buff_controller ────────────────┤
               │                                            ↓
               │                                      combat_gimbal → 云台/射击
               │
               └─ 自身状态/敌情 ──────────┐
                                         ↓
地图 → static_grid_publisher → dijkstra_planner → path_follower → 底盘速度
```

正式入口：`run_competition_auto.sh` → `launch/competition_auto.launch.py`。实际节点只有下面八个；运行时还会按启动参数加载坐标变换与 RViz。

## 八个比赛节点

以下源码路径均以 `src/stage1_comm_test/src/` 为起点。

| 节点 | 源码入口 | 负责的内容 |
| --- | --- | --- |
| `armor_detector` | `detection/armor_detector.cpp` | 图像灯条提取、装甲配对、数字分类、PnP 位姿观测 |
| `tracker` | `tracking/tracker.cpp` | 刚体目标跟踪、装甲板关联、状态估计与预测 |
| `aim_solver` | `aiming/aim_solver.cpp` | 弹道补偿、预测瞄准和开火条件计算 |
| `combat_gimbal` | `aiming/combat_gimbal.cpp` | 协调装甲板瞄准、能量机关、搜索和行进朝向；统一输出云台与射击指令 |
| `buff_controller` | `buff_detection/buff_node.cpp` | 能量机关视觉、旋转运动估计、回合/扇叶切换及单发意图 |
| `static_grid_publisher` | `mapping/static_grid_publisher.cpp` | 加载当前静态地图、膨胀图和坡道/高地标注 |
| `dijkstra_planner` | `navigation/dijkstra_planner.cpp` | 比赛任务调度、攻击位置选择和全局 Dijkstra 路线 |
| `path_follower` | `navigation/path_follower.cpp` | 路线执行、速度/加速度约束、局部碰撞检查、停车与恢复 |

## 答辩可以重点讲的实现

**装甲板视觉。** `detection/armor_detection.hpp` 用颜色、亮度、灯条形状及配对几何得到候选。`classification/number_classifier.hpp` 使用现有 ONNX 数字模型判断身份；这是数字分类，不能把整条检测链描述成 YOLO 检测。`geometry/aim_geometry.hpp` 负责坐标变换、投影和装甲板 PnP 几何。

**跟踪与预测。** `tracking/rigid_tracker.hpp` 维护整车刚体及装甲板槽位状态，区分实测观测和短时预测。`tracking/reprojection.hpp` 用于投影及目标选择。帧时间戳、序号与新鲜度检查位于 `common/ros_aim_utils.hpp` 等共享代码中。

**瞄准与发弹。** `aiming/ballistics.hpp` 处理弹道，`aiming/fire_control.hpp` 等文件处理瞄准和发弹许可。统一控制器 `combat_gimbal.cpp` 防止多个模块同时抢写云台。能量机关还使用 `rune_single_shot.hpp` 等单发确认逻辑，不能把命令发出、实际耗弹和命中视作同一件事。

**大小能量机关。** 共用传统视觉基础，不使用 YOLO。`buff_visual.hpp`、`buff_r_center.hpp` 处理视觉与 R 中心；`buff_motion.hpp`、`big_rune_motion.hpp` 分别承担运动估计；`rune_leaf_cycle.hpp`、`big_rune_cycle.hpp` 处理扇叶/回合切换。大小符转动和亮起方式不同，不能用同一套匀速处理替代。

**规划与任务。** `navigation/dijkstra.hpp` 是 Dijkstra 实现。`assault_mission.hpp`、`mission_order.hpp`、`rune_mission.hpp` 参与机器人、能量机关、前哨站、基地和补给的任务安排。开局己方能量机关与原右下坡路线保留，符往返按当前反馈调度；四号车和哨兵继续使用当前的高地站位约束。

**底盘执行。** `path_following.hpp` 处理前视、速度限制、加减速与碰撞试算。全局路线可达不等于某个即时速度一定安全，局部跟随器仍检查实际状态、动态障碍和制动。`combat_policy.hpp` 与 `motion_recovery.hpp` 处理交战停车及恢复；不会因为地图上画了路线就跳过局部执行检查。

**地图来源。** 实际比赛使用 `maps/arena_reference/`。`config/reference_terrain.yaml` 保存地形描述，`tools/build_reference_grid.py` 和 `build_arena_grid.py` 保留生成能力。几何摘要与公开地标投影报告参与启动校验；整理没有重新标定或修改地图数据。

## 接口与编号

外部游戏消息在 `campusgame_ros/ros2_auto_framework/src/tdt_interface/msg/`；内部消息在 `src/campus_aim_interfaces/msg/`。底盘主要消费 `NavigationPlan`，视觉链路主要使用 `ArmorFrame`、`TrackFrame`、`AimSolution`，能量机关使用 `BuffSolution`、`BuffStatus`。

`player_id=1` 为蓝方，`player_id=2` 为红方。数字分类标识与导航敌情编号不是所有目标都一致：视觉前哨站为 6、哨兵为 7、基地为 8；导航敌情中哨兵使用 5、前哨站 6、基地 7。映射见 `classification/armor_identity.hpp` 和 `navigation/mission_order.hpp`，答辩时应区分两套编号。

历史试验、单元/联调测试、外部参考仓库和调试录像报告已保存在完整备份 `../campusgame1/` 中，不进入精简工程的正式构建。
